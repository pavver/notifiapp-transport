# Документація для Агентів (NotifiApp Transport) - ГЛИБОКИЙ АНАЛІЗ

Цей файл містить детальний технічний опис транспортного рівня NotifiApp Transport.

## 1. Рівень Фреймінгу та Протокол (`frame.rs`)

### Структура кадру
- Кожен кадр складається із заголовка фіксованого розміру та довільного корисного навантаження.
- Заголовок містить унікальний ідентифікатор кадру `id` (UUID) для відстеження запитів та відповідей.
- Поле `kind` типу [FrameKind](src/frame.rs) визначає призначення кадру.
- Підтримуються такі типи кадрів:
  - `Handshake` - для ініціалізації Noise шифрування.
  - `AuthRequest`/`AuthResponse` - для перевірки автентифікації клієнта.
  - `Ping`/`Pong` - для підтримки активності та перевірки зв'язку.
  - `Request`/`Response` - для класичного запит-відповідь сценарію.
  - `Message` - для односторонніх асинхронних подій.
  - `Close` - для чистого закриття з'єднання.

## 2. Безпека та Шифрування Noise (`crypto.rs`)

### Рукостискання (Handshake Flow)
- Використовується патерн Noise XX (`Noise_XX_25519_ChaChaPoly_BLAKE2b`).
- Рукостискання складається з трьох кроків:
  1. Клієнт генерує та надсилає перший безіменний Noise пакет.
  2. Сервер відповідає своїм Noise пакетом та надсилає власний публічний ключ.
  3. Клієнт відповідає третім пакетом, передаючи свій публічний ключ під шифром.
- Після завершення рукостискання створюється об'єкт [NoiseSession](src/crypto.rs).
- Усі наступні кадри шифруються та дешифруються цим сеансом за допомогою AEAD ChaCha20-Poly1305.

## 3. Планування Повідомлень WFQ (`scheduler.rs`)

### Черги та Пріоритети
- Для запобігання монополізації каналу великими файлами чи неважливими даними реалізовано Weighted Fair Queueing.
- Доступні три рівні пріоритету [MessagePriority](src/scheduler.rs):
  - `High` (вага 10) - для термінових пушів та тривог.
  - `Normal` (вага 3) - для звичайних повідомлень та запитів.
  - `Low` (вага 1) - для фонової синхронізації та логів.
- Планувальник крутиться в окремому циклі та вибирає повідомлення з черг пропорційно до їхньої ваги.

## 4. WebSocket Клієнт та Цикл З'єднання (`ws/client/connection_loop.rs`)

### Життєвий цикл та Автоматичне перепідключення
- Клієнт [WsClient](src/ws/client/mod.rs) підключається до заданого через `set_endpoint` ендпоінту.
- При розриві зв'язку автоматично запускається процес перепідключення з експоненціальним відкатом (exponential backoff).
- Heartbeat цикл надсилає `Ping` кожні 30 секунд.
- Якщо відповідь `Pong` не надійшла протягом 10 секунд, з'єднання вважається розірваним і запускається перепідключення.

## 5. WebSocket Сервер (`ws/server/`)

### Обробка сесій
- Функція [accept_ws_session](src/ws/server/mod.rs) виконує Noise рукостискання з клієнтом.
- Далі вона викликає переданий [AuthHandler](src/auth.rs) для автентифікації.
- У разі успіху створюється фонова таска обслуговування сесії та повертається ручка керування [ServerSessionHandle](src/ws/server/session.rs).

## 6. Резервний HTTP та SSE транспорт (`http/`)

### SSE subscriptions
- Клієнт може підписатись на події через Server-Sent Events за допомогою [SseResponse](src/http/sse.rs).
- Сервер використовує [SseEmitter](src/http/sse.rs) для трансляції нових подій підключеним клієнтам.
- Клієнтський [HttpClient](src/http/client.rs) автоматично відновлює SSE підписку при її раптовому обриві.
